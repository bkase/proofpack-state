# T06 -- the repeated Git-state workload, measured

SPEC 11.4 asks for the acceptance workload to be measured, and SPEC 11.3 sets
the method: fixed inputs, interleaved trials, an A-versus-A noise control,
medians rather than single runs, and preprocessing counted rather than hidden.
`bench/repeated.sh` does exactly that, and it checks that `pp` agrees with
git's own difference on every cell before it reports a single timing.

Machine: Apple Silicon, macOS 25.6. Source: a clone of `bendlang/bend`,
31,516 objects reachable from `refs/heads/main`. Import: 2.7--2.9 s, once,
3.4M on disk.

## Why a single ratio would have been a lie

The two sides have different shapes. The baseline re-traverses the requirement
for every cell, so it is almost pure per-cell cost. `pp` loads the stored
generation once and then answers cells from it, so it is a large fixed cost
plus a small per-cell cost. Their ratio therefore depends entirely on the cell
count, and quoting one number would have meant quoting a chosen cell count.

An earlier version of this benchmark did quote one number, and it produced
1.59x, 1.70x and 0.47x on three consecutive runs -- a 3x spread in both
directions. The cause was not the program: it was rebuilding the receivers
into a fresh temp directory each run, so every run measured a different page
cache. With fixed receivers, warm-ups and interleaving, the noise floor here
is 0.1--2.5%.

## Regime A: small inventories (32 receivers, 135--1,937 objects each)

A worker or cache holding a slice of the history -- SPEC 1.1's actual case.

| cells | baseline | pp | pp/baseline |
|------:|---------:|---------:|-----:|
| 1 | 0.215 s | 1.070 s | 4.97x |
| 2 | 0.436 s | 1.190 s | 2.73x |
| 4 | 0.820 s | 1.269 s | 1.55x |
| 8 | 1.609 s | 1.359 s | 0.84x |
| 16 | 3.176 s | 1.616 s | 0.51x |
| 32 | 6.397 s | 2.195 s | 0.34x |

A-vs-A control at 32 cells: 6.402 s against 6.397 s, 0.1% apart.

Shapes: baseline 0.016 s fixed + 0.1994 s per cell; pp 1.034 s fixed +
0.0363 s per cell. So pp costs **81.8% less per cell** and 1.02 s more to
start. Measured crossing between 4 and 8 cells; at 32 cells pp is **2.9x
faster**. Counting the 2.72 s import as well, the predicted crossing is 22.9
cells, and 32 cells is past it.

## Regime B: near-full inventories (8 receivers, 28,771--31,516 objects each)

| cells | baseline | pp | pp/baseline |
|------:|---------:|---------:|-----:|
| 1 | 0.266 s | 1.298 s | 4.87x |
| 2 | 0.515 s | 1.466 s | 2.84x |
| 4 | 1.204 s | 2.043 s | 1.70x |
| 8 | 2.066 s | 2.716 s | 1.31x |

A-vs-A control at 8 cells: 2.014 s against 2.066 s, 2.5% apart.

Shapes: baseline 0.009 s fixed + 0.2571 s per cell; pp 1.095 s fixed +
0.2026 s per cell. pp costs 21.2% less per cell, predicting a crossing near
20 cells, but **only 8 receivers of this size were built, so pp was behind at
every cell count actually measured. There is no speed claim in this regime**
-- the crossing is arithmetic from two measured points, not an observation.
The benchmark script says so itself rather than reporting the prediction as a
result.

## What the difference between the regimes means

pp's advantage is exactly one thing: it does not re-traverse the requirement
per cell. That advantage is worth 0.199 s per cell here. Against it, pp pays
to parse each inventory's object ids, which costs roughly in proportion to the
inventory's size -- 0.036 s for a 1,000-object inventory, 0.203 s for a
30,000-object one. So the win is large when inventories are small relative to
the requirement and shrinks as they approach it, which is what the two tables
show.

That is a statement about where this design helps, and it happens to match
where the problem actually occurs: a receiver that already holds everything
does not need a tool to tell it what is missing.

## What is not claimed

* No GPU claim. These runs are CPU. Metal is dispatched and cross-checked for
  equality (see `tools/differential.sh`), and `auto` does not choose it at
  these sizes.
* No claim in regime B, for the reason above.
* No claim about repositories larger than this one, or about SHA-256
  repositories, neither of which was measured.

## Reproducing

```
fixtures/make_repos.sh                       # the differential's fixtures
bench/repeated.sh <source-repo> <receivers-dir> 5
```

The receivers directory holds bare repositories named `r0`, `r1`, ...; the
script sweeps 1, 2, 4, ... up to however many are present. It exits non-zero
without reporting timings if any cell disagrees with git.
